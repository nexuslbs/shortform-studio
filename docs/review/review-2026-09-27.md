## 1. Verdict

APPROVE

### Reasons

1. **The MVP definition is met end-to-end.** The smallest policy-compliant production line exists:
   `content/roman-concrete/script.json` (original script) → original Pillow-drawn 1080x1920 graphics
   → espeak-ng TTS → SRT captions → H.264/yuv420p + AAC 48 kHz 9:16 MP4 → `qa` gate → YouTube
   Data API v3 resumable upload (private by default, `containsSyntheticMedia` set) → `measure` leg.
   The committed `out/roman-concrete/` artifact set is complete and internally consistent.
2. **Policy compliance is mechanically enforced, not just claimed.** `qa` re-checks `#Shorts`,
   the synthetic-media disclosure sentence, `selfDeclaredMadeForKids=false`, URL well-formedness,
   affiliate disclosure when an affiliate URL exists, plus the technical delivery contract. The
   committed `out/roman-concrete/qa-report.json` shows 17/17 PASS and the tester re-ran it to
   `QA_EXIT_CODE=0`.
3. **Private-by-default and disclosure-set are correct in the code and in the wire shape.**
   `build_upload_body()` forces `status.privacyStatus = privacy` and the CLI default is `private`;
   `status.containsSyntheticMedia = true`. The dry-run log shows exactly
   `"privacyStatus": "private", "containsSyntheticMedia": true`.
4. **No credential is hardcoded and no secret is committed.** Credentials are read from the
   environment only (`YOUTUBE_OAUTH_TOKEN`, `YOUTUBE_API_KEY`). An independent search across the
   repo found only documentation placeholders (`ya29.<...>`) and the tester's own explicitly dummy
   `ya29.` strings in the committed test report; no real token, API key, or private key.
5. **No third-party asset is used.** `out/roman-concrete/provenance.json` has exactly one input
   (`content/roman-concrete/script.json`, hash-bound) and only local outputs produced by
   `espeak-ng`/`ffmpeg`/Pillow; an independent search found **zero** `http(s)://` URLs in it.
6. **The tester's findings are real but non-blocking** (see §4). None of F1/F2/U1 breaks policy
   compliance, the private default, the disclosure flag, originality, or the happy-path run. They
   are usability/verification limitations, not correctness or compliance defects.
7. **The offline mock is a legitimate, documented substitute** for a live upload in an environment
   that has no Google credential or sandbox, and the same code path serves mock and real (only the
   base URL changes). "Never fake an upload" is enforced by the exit-2 handover.

No blocking defect was found. A blocking verdict was considered (see U1) and not warranted for the

## 2. Scope-discipline judgement

**Is this the smallest thing that delivers the core value? Substantially yes.**

In scope and justified:

- **YouTube only.** Instagram Reels Graph API is deferred (as the MVP definition permits); no
  Reels code, token plumbing, or app-review work was done.
- **Measurement leg present but honest.** `measure` fetches public statistics and appends a
  snapshot; the real view-through/retention metric is explicitly deferred to the YouTube Analytics
  API and replaced by a clearly labelled `view_through_placeholder_pct` with a
  `view_through_note`. That is the right call and it is labelled in the data, not just the prose.
- **Local/free tooling instead of paid APIs.** espeak-ng (TTS) and Pillow (graphics) replace the
  plan's hypothetical paid image/TTS APIs. This is a deliberate cost/quality trade, appropriate for
  an MVP, and it keeps every asset original.
- **The mock** (`mocks/youtube_mock.py`) is ~190 stdlib lines; it is the only way to prove the
  publish/measure legs without a credential. Not scope creep - it is the evidence instrument.

Deferred correctly and **not** built: paid AI image/video APIs, dashboard/human-review UI, affiliate
network integration, volume scaling, TikTok/Pinterest/Facebook, automated analytics loop.

One genuine scope note (non-blocking):

- The plan's runbook steps 1–2 (researcher idea generation, author scriptwriting) are represented
  by a **committed hand-authored `script.json`**, not by an LLM step. For an MVP this is defensible
  and arguably safer for the "original work or significant original commentary" requirement, but it
  means the pipeline automates *production*, not *editorial ideation*. At 30 videos/month a human or
  external agent must still write each script. That is the largest gap between "MVP" and the plan's
  80–90%-automated ambition, and it should be the first thing funded in P3, not silently assumed
  done.

## 4. Rulings on the tester findings

### F1 - dry-run hides a missing token - **NON-BLOCKING** (cosmetic)

Reproduced by source reading: `publish.py` builds
`"Authorization": f"Bearer {token}" if token else "Bearer <YOUTUBE_OAUTH_TOKEN NOT SET>"`, then
`_redact_headers()` sees the `authorization` key and rewrites *any* value to
`Bearer <redacted:{len(token)} chars>`. The literal placeholder is exactly 29 chars, hence the
committed `out/selftest/publish-dry-run.log:4` shows `Authorization: Bearer <redacted:29 chars>`.
The test report reproduces the same string.

- **Why non-blocking:** no secret exists or leaks; the dry-run sends nothing; the **live** path
  already prints the full `HANDOVER_MESSAGE` and exits 2 before any socket opens. Compliance,
  privacy default, and "never fake an upload" are unaffected. The only harm is operator ambiguity
  in a *diagnostic* view that exists precisely to be read by a human.
- **Minimum change (recommended, not required to approve):** in the dry-run branch, when `token`
  is empty, print the literal header without redaction (or add an explicit
  `# token: NOT SET` line). One conditional, no behavioural change. Should land before an operator
  relies on dry-run output to confirm credentials.

### F2 - uncaught non-HTTP network errors → raw traceback, exit 1 - **NON-BLOCKING** (robustness)

Reproduced by source reading: `publish._http()` and `measure._get()` catch only
`urllib.error.HTTPError`; `cli.main()` catches only `FileNotFoundError`/`ValueError`/`RuntimeError`.
`urllib.error.URLError` (and `TimeoutError`) is an `OSError`, so a refused connection escapes to a
raw traceback and exit 1. The tester reproduced this against a dead port.

- **Why non-blocking:** the failure is **loud** (non-zero exit, never a false success) and does not
  touch policy, privacy, disclosure, or originality. It is poor operator hygiene, not a wrong
  result. The plan's "technical/API failures" kill criterion is about *persistent* failures halting
  production; this is a single cleanly-detected failure.
- **Minimum change (recommended, not required to approve):** catch `OSError` (covers `URLError` and
  `TimeoutError`) in `_http`/`_get` and raise a `RuntimeError` with the URL and reason, or add
  `urllib.error.URLError`/`OSError` to the `cli.main` except clause so the message routes through
  the existing `ERROR: ... exit 3` path. ~3 lines. Should land before unattended operation, since a
  transient blip currently produces a traceback an operator cannot triage from the console line.

### U1 - real Google endpoints never contacted - **NON-BLOCKING** (accepted, inherent limitation)

There is no Google credential and no `videos.insert` sandbox in this environment. The live upload
leg is proven only by (i) the dry-run wire shape, (ii) a full round-trip against the bundled local
mock through the *same* `publish()`/`measure()` code with only `--api-base` changed, and (iii) the
exit-2 no-credential handover that proves no fake success.

- **Why non-blocking:** the MVP definition requires an upload path, not a proven live upload, and
  the plan itself makes the channel/OAuth setup a **human first task** (plan "Concrete First Task"
  steps 1, 3, 5). Delivering the machinery plus a supervised handover is exactly the MVP contract.
  The shared-code design materially de-risks the untested hop; the request body, method, URL, quota
  cost, `privacyStatus`, and `containsSyntheticMedia` are all verified statically and against the
  mock.
- **Minimum action (required residual, not a code change):** keep this limitation documented (it
  is, in README/RUNBOOK and the tester's report) and treat the **first live upload as a
  supervised human-handover test** before any unattended use. A real operator must confirm: OAuth
  consent/scope, HTTP 200 from `videos.insert`, video lands **private**, `containsSyntheticMedia`
  shows in Studio, and the returned `id` round-trips through `measure` with a real API key.

**Summary:** no blocking finding. All three are non-blocking; F1 and F2 have small recommended
fixes, U1 has a required operational control.

## 5. Risks and kill criteria

### Kill criteria restated from the plan (these remain the governing stop rules)

1. **Low engagement** - consistently low Avg View Duration (<20%), CTR (<1%), stagnant/declining
   subs/followers, with **no significant improvement after 3 months of strategic adjustments**.
2. **Platform policy violations** - **2–3 YouTube strikes in 90 days**, permanent
   demonetisation, or account termination.
3. **Unprofitable** - consistent losses (>200% costs vs revenue) for 6 months after monetisation,
   or **still unprofitable for >12 months** with no clear path to growth after cost/strategy
   optimisation.
4. **Technical/API failure** - persistent, unresolvable issues **halting production >1 week**, or
   recurrent failures requiring constant manual intervention.

### MVP-specific risks

- **R1 (highest): "significant original commentary" is a human/platform judgement the QA gate
  cannot make.** `qa` mechanically proves the assets are original and the disclosure is present;
  it cannot prove the video is not "templated/low-value mass upload" as YouTube defines it. A
  drawn-slide + TTS explainer at volume is exactly the shape the inauthentic-content policy
  targets. Mitigation: keep scripts genuinely researched (the Roman-concrete script is), vary
  format, and watch strikes (kill criterion 2) rather than assuming PASS = monetisable.
- **R2: first live upload is unverified (U1).** Mitigation: supervised first upload (above).
- **R3: disclosure placement.** The committed description places the synthetic-media sentence
  *after* the title and summary (~287 chars in), i.e. likely **below the "…more" fold**, while
  `docs/research/platform-rules-2026-09-27.md` says the disclosure should be *above* it for
  YouTube, and the affiliate disclosure (when later injected) is appended after the AI sentence,
  also below the fold. Not blocking today: the actual YouTube compliance mechanism,
  `status.containsSyntheticMedia`, is set in the API request, and no affiliate link is present.
  Mitigation before adding affiliate links: move the disclosure sentence to the first paragraph.
- **R4: placeholder metric misuse.** `view_through_placeholder_pct` is a like/comment/view proxy,
  not retention. It is labelled in the JSONL and stdout, but a future dashboard could mistake it
  for the real metric. Do not report it as view-through.
- **R5: secret handling on the real path.** Credentials are env-only and the mock redacts
  `Authorization`; the committed `mocks/transcript.log` shows `<redacted:15 chars>` for the dummy
  token. Risk is operational (never `git add` a real transcript; never export a token into a
  logged shell). The `.gitignore` covers `.env`, `*.token`, `*oauth*.json`,
  `client_secret*.json`, `credentials.json`.
- **R6: API drift.** `containsSyntheticMedia` and resumable-upload semantics can change; the first
  live upload also doubles as a compatibility check.

### What a real operator must watch

- Run `qa` and require exit 0 before any upload; the default remains `private`.
- Review the private video in YouTube Studio (title, thumbnail, AI disclosure, kids flag) before
  flipping privacy.
- Confirm the returned real `video_id` measures successfully with a real API key.
- Track the four leading-indicator families (content performance, audience growth, production
  efficiency, policy compliance) privately; do not expose the placeholder as retention.
- Never commit tokens; rotate them if a transcript containing a real `Authorization` is ever
  produced.
